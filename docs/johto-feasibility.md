# 성도(2세대) 지역 타당성 검토 (johto-feasibility)

성도 J1~J5(v0.16.0~v0.20.0, 2026-09-26 버전 재번호 기준)를 시작하기 전에 **만들 수 있는지, 얼마나 큰지, 무엇이 먼저인지**를 정리한 검토서다. 계획만 담는다. 코드·데이터·빌드는 바꾸지 않았다.

- 기준: 이 저장소 `rocket-trio` @ `fd88114d7`, 롬 `pokemonthyl.gba`(실사용 15,440,067바이트 = 14.72MB / 16MB)
- 참조 원작: pret/pokecrystal @ **`e058e4f50b3bbf7377e036b81c25a72c54656c5c`**(2026-09-22). `/root/src/pokecrystal`에 얕게 복제, **읽기 전용, 저장소 밖**
- 사용자 확정 전제: 마스터 플랜 Q1 = **B 축약 본토(약 95맵, 5릴리스)**. 새 그림은 FR/LG 화풍, 원작 대사 복사 금지, 양자택일 전부 지급, 전설 한 플레이 한 번(§5.9 Q4), 세이브 구조 불변(`docs/team/log.md`)
- 숫자 출처: pokecrystal `constants/map_constants.asm`(맵 크기), `data/maps/maps.asm`(타일셋·랜드마크), `maps/*.asm`(오브젝트·표지판·좌표 이벤트·대사 줄), `data/tilesets/*_metatiles.bin`(블록 수). 집계 스크립트는 작업 폴더에서 한 번 돌렸고 저장소에 넣지 않았다
- 지명: 연두마을(New Bark)·무궁시티(Cherrygrove)·도라지시티(Violet)·고동마을(Azalea)·금빛시티(Goldenrod)·인주시티(Ecruteak)·담청시티(Olivine)·진청시티(Cianwood)·황토마을(Mahogany)·검은먹시티(Blackthorn)

> **요청 문구의 도시 대응 정정**: 방울탑·불탄탑은 **인주시티**, 등대·모래사장은 **담청시티**, 모다피탑은 **도라지시티**에 있다. 이 문서는 이 대응으로 쓴다.

## 1. 2세대와 3세대의 그래픽·맵 구조 차이

### 1.1 형식 비교

| 항목 | 2세대(pokecrystal, GBC) | 3세대(이 저장소, FR/LG) | 성도 제작에 주는 뜻 |
|---|---|---|---|
| 타일 | 8×8, **2bpp(4색)** | 8×8, **4bpp(16색)** | 2세대 타일은 색 정보가 1/4. 변환해도 FR/LG 명암 단계(4~6단)가 안 나온다 |
| 팔레트 | 배경 팔레트 8개 × 4색, 시간대(아침·낮·밤)마다 바꿈 | 프라이머리 7 + 세컨더리 6 = 13개 × 16색(0번 투명) | 팔레트를 새로 설계한다. 시간대 색 변화는 FR/LG에 없음(3.4) |
| 맵 단위 | **블록 32×32px**(타일 4×4) | **메타타일 16×16px**(타일 2×2 × 2층 = 8타일) | 블록 1개 = 메타타일 2×2. 원작 맵 W×H 블록 → 2W×2H 메타타일 |
| 충돌 | 블록마다 16×16 사분면 4칸의 충돌값(`COLL_*`) | 메타타일마다 행동값(`MB_*`) + 층 종류(보통·덮음·분할) 32비트 속성 | 사분면 = 메타타일이라 **통행 구조는 1:1로 대응**한다. 그림은 대응하지 않는다 |
| 층 | 없음(스프라이트 우선순위 비트만) | 아래층·위층 두 겹. 나무 위·다리 밑·지붕 끝이 위층 | 위층 설계(인물이 지붕 뒤로 들어가는 곳)를 새로 해야 한다 |
| 타일셋 크기 | 타일 192(+공용), 블록 64~128 | 프라이머리 640타일·640메타, 세컨더리 **384타일·384메타**(`include/fieldmap.h:6-9`) | 세컨더리 하나에 도시 하나가 넉넉히 들어간다 |
| 타일셋 수 | 36개(성도 맵이 쓰는 것 34) | 이 저장소 칸토 약 60 + 에메랄드 63 | 신규는 12~16개로 충분(3장) |
| 맵 스크립트 | RGBDS 매크로, 2세대 스크립트 명령(`checkevent`, 전화·라디오) | `.inc` 매크로, 3세대 스크립트 명령 | 명령 대응이 없다. 흐름만 읽고 새로 쓴다 |
| 야생표 | 풀숲 7칸(30/30/20/10/5/4/1%) × 아침·낮·밤, 물 3칸, 낚시는 그룹별 | 풀숲 12칸, 물 5칸, 낚시 10칸. 이 저장소는 아침·밤 표 지원(`docs/dex-habitat.md` 1.1) | 칸 수·확률이 달라 **재배분**한다(4.2) |

### 1.2 에메랄드 이식 도구를 성도에 쓸 수 없는 이유

| 이식 단계(`docs/hoenn-import.md`) | 에메랄드 → FR/LG | 크리스탈 → FR/LG |
|---|---|---|
| 타일셋(`import_tilesets.py`) | 같은 4bpp PNG. 속성만 u16 → u32 변환 | 2bpp·4색. **변환 자체를 하지 않는다**(원칙, 4장) |
| 맵·레이아웃(`import_maps.py`) | 같은 `map.json`·`map.bin` 형식. 이름만 바꿈 | 블록 배열 + asm 이벤트. 메타타일 번호가 대응하지 않음 |
| 스크립트·대사(`port_events.py`, `rewrap_text.py`) | 같은 스크립트 언어. 대사는 줄바꿈만 | 스크립트 언어가 다르고, 대사는 **새로 쓴다** |
| 트레이너(`import_trainers.py`) | 같은 구조체 | 파티 형식·클래스·DV가 다름. 수치만 참고 |
| 음악(`import_music.py`) | m4a MIDI | GBC 사운드 명령. 이식 불가(4.3) |
| 결과 | 457맵 지형이 한 번에 들어옴 | **자동으로 들어오는 맵은 0개.** 참고 수치 추출만 가능 |

## 2. 성도 타일셋 제작 방법

### 2.1 원칙

| 원칙 | 내용 |
|---|---|
| 화풍 | FR/LG 화풍(`docs/team/log.md` 2026-09-23). 윤곽선·명암 방향(왼쪽 위 광원)·채도는 FR/LG 칸토 타일셋에 맞춘다 |
| 원천 | ① FR/LG 타일 그대로 ② FR/LG·에메랄드 타일 재조합·재색칠 ③ 팀이 새로 그린 타일. **2세대 타일 그래픽의 4bpp 변환은 하지 않는다** |
| 생성기 | 타일셋마다 `tools/johto/make_<tileset>.py` 한 개. 재활용 타일은 "원본 타일셋 + 타일 번호 + 팔레트 처리"로 기록하고, 새 타일은 팀이 그린 PNG를 합친다. 선례: `tools/make_runway_tiles.py`(새 타일을 세컨더리 끝에 추가), `tools/make_silver_mountain.py`(불씨산 타일 재색칠), `tools/make_airport_lounge.py`(에메랄드 세트 복사 + 새 타일) |
| 프라이머리 | 야외는 FR/LG `gTileset_General`, 실내는 `gTileset_Building`을 그대로 쓴다. 풀숲·나무·길·물·문이 칸토와 같은 모양이 되어 "같은 게임"으로 보인다 |
| 에메랄드 세트 | 에메랄드 세컨더리(`em_*`)는 에메랄드 프라이머리(`EmGeneral`/`EmBuilding`)와 짝이다(`isEmerald`, `src/fieldmap.c:438`). 성도 야외에는 **통째로 쓰지 않고 필요한 타일만 새 FR/LG 형식 세컨더리로 복사**한다. 실내·동굴은 에메랄드 짝을 통째로 써도 된다 |
| 승인 | 디자이너 제작 → 일러스트레이터 그림체 점검 → **예술감독 APPROVED** → 출시. 시안은 예술감독 승인 뒤 사용자에게 |

| 단계 | 방법 |
|---|---|
| 작업 지시 | 성도 관련 모든 에이전트 지시에 "허용 출처만" 문장을 넣는다(`.claude/agents/designer.md`·`illustrator.md`에 한 줄 추가를 프로듀서가 검토) |

### 5.3 에셋 출처 기록(provenance)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 생성기 + 출처 표(추천)** | 세트마다 `tools/johto/make_<set>.py`가 "원본(FR/LG 세트·타일 번호) + 처리(재색칠 규칙)" 또는 "팀 PNG(작성자·날짜)"로 타일을 조립. 같은 정보를 `docs/team/art/johto/provenance.md` 표(세트·타일 범위·원천·작성자·승인 문서)로 남김 | 다시 돌리면 같은 결과 = 유래 증명. 이 저장소 방식(`tools/make_*.py`)과 같음 | 생성기 작성 시간 |
| B. 파일별 출처 표만 | PNG마다 표 한 줄 | 간단 | 타일 단위 증명이 약함 |

- 팀이 새로 그린 PNG는 시안 단계부터 저장소에 두고(커밋은 프로듀서), 예술감독 판정 문서 경로를 출처 표에 적는다. 중간 시안 이력 자체가 "새로 그렸다"는 증거가 된다.

## 8. 결론

- **착수 가능.** 단, 호연 이식처럼 "들여와서 채우는" 일이 아니라 **새 지역을 짓는** 일이다. 필요한 것은 인력(특히 타일)과 선행 검증 다섯 가지다.
- 기술적으로 막는 것은 없다. 세이브 구조를 바꾸지 않고 들어간다(맵 그룹·MAPSEC·플래그·변수·트레이너 비트 모두 여유). 스프라이트 번호만 코드 해법이 필요하다.
- 원칙(FR/LG 화풍, 원작 그래픽·음악·대사 미사용, 팬 자원 미참조)은 생성기 + 출처 표 + 예술감독 체크리스트로 지킬 수 있다.
