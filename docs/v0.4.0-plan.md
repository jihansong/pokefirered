# v0.4.0 · v0.5.0 구현 계획

스타터 피카츄 강화(v0.4.0)와 로켓단 확장(v0.5.0), 그리고 옐로에서 가져온 그래픽을 FRLG 화질로 맞추는 작업을 함께 정리한다.
승인 전에는 코드를 건드리지 않는다.

## 브랜치와 공통 규칙

| 브랜치 | 내용 | 릴리스 |
|---|---|---|
| `starter-pikachu` (master에서 분기) | 1~4번 + 옐로 유래 그림 중 피카츄 관련(0-A~0-C) | v0.4.0 |
| `rocket-expansion` (v0.4.0을 master에 머지한 뒤 master에서 분기) | 5~6번 (로사·로이 그림 = 0-D 포함) | v0.5.0 |

- 작업 하나마다 커밋. 단계가 끝날 때마다 `make leafgreen` 통과, `saves/v0.1.0.sav`·`saves/v0.2.1.sav` 로드 IDENTICAL, 60fps를 확인한다.
- 세이브 구조는 바꾸지 않는다. 새 플래그·변수는 비어 있는 번호만 쓴다(플래그 0x210~, 변수 `VAR_0x40xx` 빈 칸).
- 새 이벤트와 바뀐 규칙은 게임 안 NPC가 알려 주게 하고, `docs/events-roadmap.md`와 공략집에 기록한다.
- 브랜치 머지·태그·패치·릴리스는 캡처를 확인받은 뒤에만 한다.

## v0.4.0 — `starter-pikachu`

### 1. "오 박사의 피카츄" 판별 비트

현재 상태: `src/starter_pikachu.c`에 `IsStarterPikachu()`가 이미 있다. 파티 슬롯은 보지 않는다. 판별 기준은 다음 넷이다.

- `FLAG_RECEIVED_STARTER_PIKACHU`가 켜져 있다.
- 종족이 피카츄다.
- 성격값이 받을 때 저장한 `VAR_STARTER_PIKACHU_PERSONALITY_LO/HI`와 같다.
- 어버이 ID와 이름이 플레이어다.

그래서 지금도 PC 보관·파티 순서 변경 뒤에 유지되지만, 세이브 변수에 의존하므로 다른 세이브(교환)로 가면 풀린다. 동행·기분·감정·천둥의돌 거부·서핑 보드 색이 모두 이 함수를 쓴다.

**결정:** 판별을 BoxPokemon 비트 하나로 **통일**한다. `IsStarterPikachu()` = 종족 피카츄 && 비트 1이다. 옛 기준은 기존 세이브를 한 번 이전할 때만 쓴다.

건드릴 파일

- `include/pokemon.h` `struct BoxPokemon`: `u8 unused:4`에서 1비트를 떼어 `isStarterPikachu:1` / `unused:3`으로 만든다. `blockBoxRS`는 건드리지 않는다. 이 바이트는 암호화된 서브스트럭처 밖이라 체크섬과 무관하다. PC 보관이나 교환 때 구조체째 복사되므로 비트가 유지된다.
- `include/constants/pokemon.h`: `MON_DATA_STARTER_PIKACHU` 추가. `src/pokemon.c`의 `GetBoxMonData`/`SetBoxMonData`에 case를 추가한다.
- `src/starter_pikachu.c`
  - `RecordStarterPikachu()`에서 비트를 세팅한다. 기존 성격값 저장은 기분·감정 시스템이 쓰므로 유지.
  - `IsStarterPikachu()`를 "종족 == 피카츄 && 비트 == 1"로 바꾼다. 동행·기분 등 기존 호출부도 모두 이 함수를 그대로 쓴다.
  - **기존 세이브 이전:** 이어하기 할 때 한 번 파티와 PC 전체를 돌면서, 옛 방식(성격값+OT)으로 맞는 피카츄에 비트를 세운다. `src/overworld.c` `CB2_ContinueSavedGame`에서 호출한다.

리스크

- 교환으로 받은 남의 "오 박사의 피카츄"도 비트가 있으므로 스타터로 취급된다. 파티에 둘이면 동행은 파티 앞쪽의 한 마리가 맡는다(`GetStarterPikachuPartySlot`이 첫 번째를 돌려줌). 같은 핵끼리 통신 교환해야만 생기는 경우다.
- 기존 세이브 이전 때 파티의 스타터 피카츄 한 바이트(오프셋 0x13, 비트 하나)가 바뀐다. 세이브 테스트에서 그 1비트만 달라지는 것을 확인하고 보고한다.
- 이 비트는 원작 FRLG·RSE로 보내도 대개 남지만, 원작에서는 아무 효과가 없다.

### 2. 전설급 능력치 + HP 추가 성장

**적용 시점: 처음부터.** 연구소에서 Lv5로 받는 순간부터 전용 종족값과 HP 추가 성장이 적용된다. 각성 이벤트는 없다. 기존 세이브의 피카츄는 이전(1번) 뒤 다음 능력치 계산(레벨업·PC 인출·전투 후)부터 적용된다. 이어하기 할 때 파티를 한 번 다시 계산해서 바로 반영한다.

- `src/pokemon.c` `CalculateMonStats()`(2103행)에서 `IsStarterPikachu`면 종족값을 전용 표로 바꾼다.
  - 기본안: HP 100 / 공격 105 / 방어 85 / 특공 130 / 특방 100 / 스피드 140. 전용 표는 `src/data/pokemon/starter_pikachu.h`에 둔다.
  - 요약 화면의 능력치 표시는 이미 이 계산 결과를 읽으므로 따로 바꿀 필요가 없다.
- 최대 HP에 `level * 3`을 더한다. 추정치(개체값 31, 노력치 최대 기준): Lv30 약 234, Lv50 약 347, Lv100 약 704. 999를 넘지 않는다.
- 현재 HP 비율은 기존 코드처럼 최대 HP 증가분만큼 현재 HP를 올리는 규칙을 그대로 쓴다.
- 확인할 것
  - 요약 화면과 전투 HP 숫자의 세 자리 표시
  - 레벨업 창의 능력치 증가 표시(`DrawLevelUpWindowPg1`)
  - PC에서 꺼낼 때 다시 계산되는지
- 리스크: 전투용 능력치 계산은 `CalculateMonStats`를 거쳐 `gBattleMons`로 복사되므로 한 곳만 바꾸면 된다. 진화 거부·동행과는 독립적이다.

### 3. 전용 레벨업 기술 + 새 기술 "볼트스트라이크"

- 학습표: `src/data/pokemon/level_up_learnsets.h`에 `sStarterPikachuLevelUpLearnset[]`를 추가하고, `GetLevelUpLearnsetForMon(mon)` 헬퍼를 둔다. 이 헬퍼로 바꿀 곳은 다음 셋이다(`src/pokemon.c`).
  - `GiveBoxMonInitialMoveset`(2277행 부근)
  - `MonTryLearningNewMove`(2294행)
  - 기술 되살리기 `GetMoveRelearnerMoves`(5784행)와 그 개수 함수
- 학습표는 요청안 그대로 넣는다. 에어로블라스트·사이코부스트·러스터퍼지·신속·볼트태클은 모두 3세대에 이미 있는 기술이다.
- 새 기술 `MOVE_VOLT_STRIKE`(355)는 전기·물리, 위력 130, 명중 85, PP 5, 20% 마비(`EFFECT_PARALYZE_HIT`). 3세대는 타입으로 물리·특수를 나누므로 전기 기술은 자동으로 특수가 된다. "물리"로 하려면 판정 예외가 필요하다. **확인 필요**: 3세대 규칙대로 특수로 둘지(추천), 예외를 둘지.
- 새 기술을 넣을 때 고칠 곳은 `MOVES_COUNT` 355 → 356과, 기술 번호로 인덱싱하는 표 전부다.
  - `include/constants/moves.h`
  - `src/data/battle_moves.h`
  - `src/data/text/move_names.h`(12자 이하, "VOLT STRIKE")
  - `src/move_descriptions.c`
  - `data/battle_anim_scripts.s` `gBattleAnims_Moves`(볼트태클 애니를 복제하고 색만 바꿈)
  - `src/battle_script_commands.c`와 `src/pokemon_storage_system_data.c`의 `MOVES_COUNT` 사용처 점검
- 여유 확인 결과: 아래 이유로 **추가에 문제없다**.
  - 기술 번호로 인덱싱하는 표는 모두 `MOVES_COUNT`로 크기가 정해진다: `gBattleMoves[MOVES_COUNT]`, `gMoveNames[MOVES_COUNT]`, `gMoveDescriptionPointers[MOVES_COUNT - 1]`, 저장소의 제한 목록 끝 표시. 356으로 올리면 함께 늘어난다.
  - 레벨업 학습표는 기술 번호를 9비트(`LEVEL_UP_MOVE_ID` 0x1FF, 최대 511)로 담는다. 포켓몬 데이터의 기술 칸은 u16이다.
  - 이름 "VOLT STRIKE"는 11자로 한도(`MOVE_NAME_LENGTH` 12) 안이다.
  - 배틀 애니 표 `gBattleAnims_Moves`는 `Move_PSYCHO_BOOST` 다음의 `Move_COUNT` 앞에 한 줄을 넣으면 된다.
  - 손으로 늘려야 하는 곳은 기술 이름·설명·애니 항목 3곳뿐이다. 빠지면 빌드 에러나 크기 불일치 경고가 난다.
- 리스크: 빌드 뒤 기술 이름·설명·애니·데미지를 에뮬레이터로 확인한다. 손가락흔들기로도 나올 수 있게 된다(원작 규칙상 자연스러움).
- 기존 1부-9 이벤트(무인발전소 볼트태클, 피카츄 서핑 가르침)는 그대로 둔다. 학습표에 이미 있는 기술을 가르치면 원작처럼 "이미 알고 있다"로 처리된다.

### 4. 파도타기 + 헤엄치는 피카츄

- `CanMonLearnTMHM()`(`src/pokemon.c` 5765행): `IsStarterPikachu`면 HM03을 허용한다.
- 파도타기를 시작하는 두 경로
  - 파티 메뉴에서 쓸 때: `gFieldEffectArguments[0]` = 파티 슬롯
  - 물가에서 A를 눌러 쓸 때: `checkpartymove` 결과 슬롯
- 두 경로 모두 `FldEff_UseSurf`(`src/field_effect.c` 2986행)를 지나므로, 여기서 슬롯이 스타터 피카츄인지 새 변수 `VAR_SURF_PIKACHU`(빈 `VAR_0x40xx` 하나)에 기록한다. 파도타기에서 내릴 때 0으로 되돌린다.
- 변수를 세이브에 남기는 이유: 파도타기 중에 저장하고 이어하면 `PlayerAvatarTransition_Surfing`(`src/field_player_avatar.c` 734행)이 서프 블롭을 다시 만드는데, 그때도 피카츄로 나와야 하기 때문이다.
- `FldEff_SurfBlob`(`src/field_effect_helpers.c` 945행): 변수가 1이면 새 필드 이펙트 템플릿 `FLDEFFOBJ_SURF_PIKACHU`로 만든다. 바운스(`SetSurfBlob_BobState`)와 플레이어 위치 보정 코드는 그대로 쓴다.
- 그림 `graphics/field_effects/pics/surf_pikachu.png`: 32×32, 4방향 × 2프레임(앞발 젓기). 동행 피카츄 필드 스프라이트에 `surf_blob.png`의 물결을 합성하는 스크립트를 `tools/make_surf_pikachu.py`로 남긴다.
- 팔레트는 동행 피카츄 팔레트를 새 태그로 동적 슬롯(12~15)에 올린다. 공항 비행 효과와 같은 방식이고, 날씨가 한 칸을 쓰므로 여유는 3칸이다.
- 기존 1부-10 "서핑 보드 색" 처리(`src/surfing_pikachu.c` `TryUseSurfboardPalette`)와 겹친다.
  - 제안: 스타터 피카츄가 직접 헤엄칠 때는 새 스프라이트를 쓴다. 다른 포켓몬이 파도타기할 때는 서핑 보드 색을 없애고 원래 블롭으로 되돌린다.
  - **확인 필요**: 보드 색을 남길지.
- 리스크
  - 파도타기 중 숨겨지는 동행 피카츄와 동시에 보이면 안 된다.
  - 폭포오르기·잠수·낚시·자전거 전환 경로가 블롭을 다시 만드는 곳을 모두 점검해야 한다(`SetSurfBlob_BobState` 호출부 4곳).

  - FRLG 더블배틀은 상대 그림이 한 장이라, 쌍둥이·젊은 부부처럼 **두 사람을 64×64 한 장에 담는다**.

  - 각자 그림을 따로 띄우려면 에메랄드식 2인 트레이너 전투를 이식해야 한다. 엔진 변경이 커서 제안하지 않는다.
- 필드 스프라이트는 조무래기(`OBJ_EVENT_GFX_ROCKET_F/M`)를 다시 기준으로 삼아 머리만 편집한다. 두 사람이 한 팔레트 태그를 함께 쓴다(기존 `jessie_james.pal`을 16색 안에서 다시 짠다).
- 비교 이미지: 조무래기와 나란히 놓은 원본/결과를 `docs/screenshots/jessie_james_compare.png`로 저장해 보여 드린 뒤 확정한다.

### 6. 로켓단 이벤트 확장

공통

- 기존 4회 대결(달맞이산 B2F, 로켓단 아지트 B4F, 포켓몬타워 7F, 실프 11F)은 유지하고, 그 사이를 이벤트로 채운다.
- 이벤트마다 플래그 1개(0x210~ 빈 번호)와 맵 스크립트로 독립시킨다. 본편 진행을 막지 않는다.
- 등장 구호는 새로 쓴 대사로 한다. BGM은 기존 `MUS_ENCOUNTER_ROCKET`을 쓰고, 전용 곡은 쓰지 않는 것을 기본으로 한다.
- 퇴장은 공용 special `RocketTrioBlastOff`로 만든다. `SE_M_EXPLOSION` + 화면 흔들림 뒤, 두 사람(과 나옹) 오브젝트가 위로 날아가며 작아져 사라지는 태스크다.
- 첫 만남(이벤트 1)에서 나옹이 "저 피카츄는 보통이 아니다"라고 알아채고, 이후 모든 등장의 동기가 된다(2번 강화와 연결).
- 트레이너 ID는 `NUM_TRAINERS` 744 → 최대 768(빈 24칸)과 `TRAINER_UNUSED_*` 자리를 쓴다. 파티는 `src/data/trainers.h` / `src/data/trainer_parties.h`에 단계별로 둔다.
  - 아보→아보크, 도가스→또도가스(실프 이후)
  - 로이: 우츠동, 잉어킹→갸라도스 개그
  - 로사: 내루미
- 새 이벤트마다 힌트 NPC를 둔다. 기존 소문 수집가(무지개시티·1의섬)에게 문장을 추가한다.

## 순서

1. `starter-pikachu`: 1 → 2 → 3 → 4 → 0-B → 0-A(샘플 확인 후 전체) → 0-C → 문서·공략집 → 확인 → v0.4.0
2. `rocket-expansion`: 5(비교 이미지 확인) → 공용 연출(구호·퇴장 special) → 6번 이벤트 1~12 순서대로(이벤트마다 커밋·빌드·세이브 테스트) → 문서·공략집 새 장·색인 → 확인 → v0.5.0

**릴리스 배정 확정:** 0-A(감정 초상화)·0-B(감정 말풍선)·0-C(타이틀 피카츄)는 모두 피카츄 그림이라 v0.4.0에 남긴다. 0-D(로사·로이 전투 그림)는 v0.5.0 5번에서 한다. 옐로 유래 그래픽은 이 넷이 전부다.
